# ADR-0029：学生用户名登录与 V1 用户迁移

- 状态：已采用（2026-11-18 用户确认：加用户名字段、邮箱和用户名都能登录、迁移 V1 老用户、允许长期无邮箱）
- 日期：2026-11-18
- 关联：ADR-0011（本 ADR 取代其「不引入用户名」「不迁移 v1 旧用户」两条，其余不变）

## 背景

V1（`Web/nhg-manabi-api`）学员以 `username` 登录，`email` 可空（B4 代建账号无邮箱）。V1 注册规则为 `^[a-z0-9_]+$`，但代码注释写明该规则「仅注册校验，存量代建账号不受影响」，所以存量用户名可能含大写或其他字符。V1 口令为 `pbkdf2_sha256$<salt>$<hex>`（PBKDF2-HMAC-SHA256，120000 次，盐按 UTF-8 字符串使用）。`App/manabi_api`（iOS 用）已废弃，不迁移。

## 决定

1. **`users` 增加 `username`**：可空、全表唯一，数据库 CHECK `^[a-z0-9_]{1,64}$`（只存小写）。**不允许含 `@`**，因此登录框内容含 `@` 即邮箱，否则即用户名，无歧义。
2. **`users.email` 改为可空**（仍唯一，仍小写）；新增 CHECK：`email` 与 `username` 至少有一个。允许 V1 无邮箱账号**长期**无邮箱。
3. **登录接口接受 `identifier`**（邮箱或用户名，大小写不敏感）；旧参数名 `email` 继续兼容。失败口径、统一 401、锁定列、等价耗时均不变；锁定按所查到的账号行计数，因此换邮箱/用户名不能绕过。
4. **V1 口令哈希原样导入**，`verify_password` 按前缀分发（`scrypt` / `pbkdf2_sha256`）；V1 用户登录成功后**当场重哈希为 scrypt**，不保留旧哈希。不建 legacy 表。
5. **无邮箱账号没有自助找回**：管理端新增「重置密码」（生成一次性展示的临时口令、撤销全部会话、清锁、写审计 `user_password_reset`）。绑定邮箱/修改用户名的自助入口本次不做。
6. **新用户注册不变**（仅邮箱 + 密码）；本次不提供注册时设置用户名。
7. **导入脚本**（`python -m app.v1_user_import`）：只读连接 V1 库，默认 dry-run，`--apply` 才写入；按 `legacy_v1_user_id` 幂等。用户名转小写后仍不符合规则、或与已有用户名/其他 V1 用户冲突、邮箱与 v2 已有账号冲突的，按规则跳过或去掉邮箱，并在报告中逐条列出，不静默改名。V1 的昵称/等级/头像/激活/停用时间保留；学习记录**不迁移**（V1 题目 ID 与 v2 Canonical 不通用）。

## 影响

- 迁移 `0019_username_login`：加列、放开 email、CHECK、审计 action 白名单加 `user_password_reset`；downgrade 在存在无邮箱用户时拒绝执行（避免丢账号）。
- 管理端用户列表/详情显示并可搜索用户名；Dashboard 的「有效用户」邮箱排除规则需对 NULL 邮箱安全。
- 学生端登录框改为「邮箱或用户名」；个人资料 DTO 的 `email` 变为可空并新增 `username`。
- 风险：无邮箱账号口令只能管理员重置；V1 导入后 V1 与 v2 并行时，两边口令改动互不同步（建议导入当天冻结 V1 注册/改密）。

## 上线步骤（生产账户不随部署自动迁移）

1. 部署：`migrate` 自动执行 `0019`，仅改表结构，不触碰用户数据。部署前按 `deployment.md` 做版本化 `pg_dump`。
2. 部署成功后，对 V1 库（只读账号）运行 dry-run：`python -m app.v1_user_import --v1-url <V1 URL>`，核对报告中的总数、无邮箱数、`degraded`/`skipped` 明细。
3. 用户确认后再加 `--apply` 导入；脚本幂等，可重复运行补入新增 V1 用户（已导入用户的口令变动不会同步）。
4. 导入前后需用户决定 V1 的冻结时点（停止注册/改密）与用户切换时点。导入属于对 V1 线上库的外部读取和对生产库的写入，必须由用户明确授权。
